## 1. 背景与问题

### 1.1 市场背景（调研摘要）
- 健康 App 2025 年收入约 $35 亿（+23.5%），健身 $34 亿（+24.5%），是传统品类增速最高两组。
- a16z 数据显示营养类 App「有收入榜席位、使用榜零席位」——付费需求真实，但产品平庸。
- 头部产品老化：MyFitnessPal 2009 年产品仍居第一；新玩家靠"拍照+AI"突围（Cal AI 2024 上线即 36 万评）。
- 用户核心痛点（Reddit/HN 1600 帖 + 800 评论）：**① 坚持不下来 ② 记录了热量但不知道"今天吃什么" ③ 菜谱与记录分离**。

### 1.2 机会点
- "拍照记录 + 个性化菜谱 + 一键购物清单"完整闭环尚无头部产品做得足够好：
  - Cal AI：拍照极简，但无菜谱闭环、无习惯养成。
  - Fitia：功能最全（拍照/语音/菜谱/购物清单/团队），但功能堆砌、更新慢。
  - Lifesum：偏"数据控"，菜谱与购物体验割裂。
- 开源参考 fud-ai 证明「BYOK + 本地优先 + AI 多提供商」架构可行且受欢迎（399★）。

### 1.3 产品定位
> **NutriMate：每天 30 秒拍一餐，AI 记录营养；想吃的时候打开就知道「今天吃什么」，菜谱一键变购物清单。**

一句话差异化：**Fitia 的功能闭环 × Cal AI 的拍照极简 × Lifesum 的习惯养成 × fud-ai 的开源本地优先架构**。

## 2. 目标用户与用户故事

### 2.1 目标用户（v0.1 圈定）
| 用户画像 | 特征 | 核心诉求 |
|---------|------|---------|
| U1 减脂小白 | 25-40 岁，想减肥但没系统方法，三餐不规律，饭局多 | 少录入、知道吃啥、能坚持 |
| U2 健身增肌者 | 有训练习惯，需要精确追踪蛋白质与热量盈余 | 快速记录、高蛋白菜谱 |
| U3 打卡型用户 | 用过 MFP/Cal AI 但中途放弃，讨厌繁琐录入 | 拍照懒人模式、低负担 |

### 2.2 用户故事（P0）
| ID | 作为… | 我想要… | 以便… | 验收要点 |
|----|-------|---------|--------|---------|
| US-01 | 新用户 | 3 步完成目标设置并得到个性化热量预算 | 知道每天该吃多少 | 预算=TDEE±盈余/赤字；宏量按目标分配；预算随身体数据更新（见 H1） |
| US-02 | U1/U3 | 拍张照片就完成一餐记录 | 不用手动搜索食物库 | 用户点击次数≤3 完成；识别结果可修正份量/名称/营养 |
| US-03 | 所有用户 | AI 不可用时手动记录 | 不阻塞记录流程 | 手动输入食物名+热量+宏量+餐次；不正确数据被校验 |
| US-04 | U1 | 打开 App 就知道今天还能吃什么 | 不再纠结"吃什么" | 基于当前时间推断下一餐，生成 3 个候选且热量在预算区间内 |
| US-05 | U1/U2 | 菜谱一键生成购物清单 | 买菜不用动脑 | 多菜谱食材自动合并去重累加 |
| US-06 | 所有用户 | 随时回看历史记录并修正 | 记录可追溯、可纠正 | 按日查看/编辑/删除；编辑后当日合计更新 |
| US-07 | 隐私敏感用户 | 自备 AI Key、数据留在本机 | 不上传隐私数据 | BYOK 配置时展示数据去向说明；本地持久化；无账号；无系统自动备份 |
| US-08 | U2 | 切换目标后预算与宏量自动重算 | 减脂结束转增肌无缝衔接 | 设置改目标→重算并持久化 |

## 3. 功能需求（P0 详细）

> 编号对应 IA 文档 F1–F9。每条含：行为描述、边界与异常、验收标准。

### F1 Onboarding（3 步向导）
- **Step1 基本信息**：性别（**仅 男/女 两选项，v0.1 不支持"其他"，避免 BMR 公式拍脑袋**）、生日、身高（cm）、体重（kg）。默认值：身高 170、体重 60。
- **Step2 目标与活动**：目标单选（减脂/增肌/维持）；活动水平 6 档：久坐(1.2)/轻度(1.375)/中度(1.55)/活跃(1.725)/非常活跃(1.9)/极活跃(2.0，重体力+每日训练)。
- **Step3 口味偏好 + 忌口**：口味标签多选（清淡/高蛋白/低碳/辣/素食/快手菜，可跳过）；**忌口/过敏多选（花生/乳制品/海鲜/麸质/鸡蛋/大豆，可跳过）**。
- **计算逻辑**：
  - BMR：Mifflin-St Jeor（男：10×kg+6.25×cm−5×age+5；女：10×kg+6.25×cm−5×age−161）。
  - TDEE = BMR × 活动系数。
  - 预算 = TDEE + 增肌（+10%）/ − 减脂（−20%）/ 维持（±0），取整。
  - **下限保护**：男 ≥1500 kcal、女 ≥1200 kcal；若触底以底线值为准，并提示"预算已接近安全下限，请结合专业建议调整"（附免责文案）。
  - 宏量能量占比：减脂 30/40/30（蛋白/碳水/脂肪）、增肌 30/45/25、维持 25/45/30；**克数 = 预算 × 占比 ÷ (蛋白4/碳水4/脂肪9)**。
- **重算时机**：每次进入 Today、日期变更、或在设置中修改身体数据/目标/活动水平时，按最新 Profile 幂等重算并持久化（`last_recalc_at` 记录最近重算时间）。注入 `Clock` 便于测试。
- **异常**：年龄<10 或>100、身高<100 或>250、体重<30 或>300 → 提示并阻止下一步。
- **验收（含黄金数值用例，domain 层 golden test）**：
  - 男/30岁/170cm/70kg/减脂/久坐(1.2)：BMR=1625，TDEE=1950，预算=1560（>1500 下限，不触发）。
  - 男/25岁/160cm/50kg/减脂/久坐：BMR=1362.5→TDEE=1635→预算=1308→触底 **1500**。
  - 女/28岁/160cm/52kg/减脂/久坐：BMR=1308.6→TDEE=1570.3→预算=1256→触底 **1200**。
  - 女/35岁/165cm/60kg/增肌/活跃(1.725)：BMR=1338.5→TDEE=2308.9→预算=2539.8→2540。
  - 宏量示例：预算 1560/减脂 → 蛋白117g/碳水156g/脂肪52g。

### F2 首页 Today
- 展示（当前日）：热量环（已摄入/预算，超支红色）、蛋白/碳水/脂肪三条进度、餐次分组列表（早/午/晚/加餐，空态提示"还没有记录"）。
- 行为：FAB「记录一餐」→ F3；「今日吃什么」入口卡 → F5；日期 < > 切换 → 历史日报（F7）；右上角齿轮 → 设置（F8）。
- **跨天定义**：冷启动或从后台恢复且 `LocalDate` 变化时重置当日统计（注入 Clock/LocalDateProvider），前台跨午夜不做实时翻转（下次恢复时更新）。
- 验收：拍照保存后首页数值实时刷新；超预算时热量环变红并提示"已超出 X 千卡"；日期切换正确；跨天恢复后重置。

### F3 拍照记录（核心闭环）
- 入口：首页 FAB / 记录一餐 Tab。
- 步骤：
  1. 输入方式选择：拍照（CameraX）/ 相册（系统 Photo Picker，无需存储权限）/ 手动（跳 F4）。
  2. **权限状态机**：首次进入拍照步骤时在上下文中申请 CAMERA；已授予→进相机；拒绝（可重新询问）→提示"需要相机权限，可用相册或手动记录"，提供"去设置"与"改用相册"两按钮；永久拒绝→同提示，仅引导去系统设置。**相册与手动路径在任何权限状态下都可用。**
  3. AI 识别：返回 `{foodName, calories, proteinG, carbG, fatG, confidence, referenceServingG, servingTip}`（**含每份参考克数 referenceServingG**，用于倍率换算）；loading 中可取消。
  4. 结果预览：食物名（**可编辑**）、营养数值（**三大宏量可编辑，AI 值仅预填**）、置信度徽标（高≥0.7/中0.4-0.7/低<0.4，低置信显示黄色警示）、份量调整（倍率 ×0.5/1/1.5/2，或自定义克数=referenceServingG×倍率）。
  5. 餐次选择：早餐/午餐/晚餐/加餐（默认按当前时间：5-10 早/10-14 午/14-21 晚/其余加餐）。
  6. 保存：写入 FOOD_LOG（source=AI_PHOTO，记录 serving_multiplier/grams/confidence）→ 返回首页刷新。
- **一图多菜**：v0.1 单图=单条记录（取主要食物，提示"多道菜请分拍"）。
- 异常/降级：
  - 未配置 AI Key → 直接提示并进入 F4。
  - 识别失败（网络）→ 指数退避重试 2 次 → 仍失败 → "识别失败，改为手动输入"。
  - 识别失败（JSON 解析）→ 重试 1 次 → 仍失败 → 降级手动。
  - **图片压缩**：识别前压缩至最长边 1024px、JPEG 质量≤80%，单请求超时 30s。
- 验收：拍照→识别→修正→保存→首页刷新（用户操作≤3 次点击核心路径）；无 Key 手动兜底；相机权限拒绝后相册/手动仍可用；取消路径可用；图片压缩后传输字节数有断言。

### F4 手动记录
- 输入：食物名称（必填）、热量 kcal（必填，0–5000）、蛋白质/碳水/脂肪 g（选填，默认 0，0–1000）、份量描述（选填）、**餐次选择（必填，默认按当前时间推断，规则同 F3）**。
- 校验：非法即提示并阻止保存。
- 保存：写 FOOD_LOG（source=MANUAL）→ 首页刷新。
- 验收：手动保存后计入当日统计且可编辑删除；餐次归组正确。

### F5 今日吃什么
- 触发：进入 Tab3 → 点「生成推荐」。
- **推荐语义（评审 H2 修订）**：按当前时间+已用餐次推断**下一餐目标餐次**（规则同 F3 餐次推断），为该餐生成 **3 个候选菜谱**；每个菜谱热量落在**剩余预算的 60%–110%** 区间；同一餐次类型内不重复；若剩余预算低于一条轻食下限（如 150 kcal）→ 空态"今日营养已达标"，不再生成。

> 若用户在非餐次时间（如下午 3 点）生成，目标餐次=距离最近的下一个餐次（如晚餐）。

- 每个菜谱含 `{name, targetMeal, calories, proteinG, ingredients[{name, amount, unit}], steps[], tips?}`。
- 展示：菜谱卡片列表（名称/热量/蛋白/目标餐次）；点卡片 → 详情（用料+步骤+营养+「加入购物清单」+已加入角标）。
- **生成限次（M10）**：每日 ≥5 次，DataStore 计数持久化，UI 显示"今日剩余 N 次"；第 6 次拦截并提示。
- 异常：
  - 已达标（剩余<150）→ 空态。
  - AI 失败 → 重试提示（消耗次数）；无 Key → 提示去设置。
  - 菜谱文本与结构化结果缓存（RECIPE_LOG）便于复用与去重计数。
- 验收：3 个候选互不相同；任一候选热量 ≤ 剩余预算×1.1；限次第 6 次被拦截；已达标显示空态。

### F6 购物清单
- 数据：`GROCERY_ITEM{name(基础食材名，不含份量), amount:Double, unit:String, checked:Boolean}`。
- 行为：加入菜谱 → 食材按**规范化基础名合并**（去空格/小写；同食材 amount 累加、unit 相同；unit 不同 → 保留两条并提示人工确认）；条目可勾选/取消/删除/清空；空态引导"去今日吃什么生成菜谱"。
- 验收：两菜谱含同一食材时仅一条且数量累加；unit 冲突时提示；勾选/删除/清空幂等；重启不丢失。

### F7 历史日报
- 行为：首页日期 < > 切换（允许未来日期，显示空态便于计划）；按日聚合餐次与热量；点击单条 → 底部弹窗编辑（份量倍率/餐次/手动改数值——倍率变更按 referenceServingG×新倍率重算营养）或删除（软删除）。
- 验收：跨日隔离；编辑重算后合计更新；删除后合计更新；软删数据不参与统计。

### F8 设置
- **身体数据（评审 H1 必改）**：体重/身高/活动水平/生日可编辑，任一修改即重算预算与宏量并持久化。
- 其他：目标切换（重算）、单位（v0.1 仅公制生效，UI 预留英制）、主题（跟随系统/浅/深）、**AI Provider 配置**（Provider 选择 + API Key 加密存储 + 模型名 + **配置时展示一次性说明：图片与文本将发往所选服务商**）、数据管理（导出 JSON / **清空业务数据**——仅清 FOOD_LOG/GROCERY_ITEM/RECIPE_LOG，保留 Profile 与 onboarding 标记，预算不变，二次确认）、关于（版本号）。
- AI Key 安全：Android Keystore AES-GCM 加密存储（沿用 video-forge-android 已验证方案）；**检测到不可解密存储（如卸载重装）→ 引导重新输入 Key**。
- 导出 JSON：写应用私有目录 + FileProvider 分享。
- 验收：改体重→预算重算；Key 加密且重启有效；配置 Provider 时有数据去向说明；清空业务数据保留 Profile；导出文件可打开。

### F9 本地存储
- Room：`PROFILE`（单行表，含 allergens、last_recalc_at）、`FOOD_LOG`（含 serving_multiplier/grams/confidence）、`RECIPE_LOG`（生成历史+结果缓存：name/targetMeal/calories/protein/ingredients JSON/steps JSON/created_at）、`GROCERY_ITEM`（amount:Double/unit）。
- DataStore：UI 偏好（主题/单位/已 onboarding/今日生成次数计数）。
- **Privacy**：manifest `android:allowBackup="false"`（不参与系统自动备份到 Google Drive）；无账号、无网络同步；所有写操作事务保证。

## 4. 非功能需求（NFR）

| 类别 | 要求 |
|------|------|

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| AI 识别准确率不足 | 核心体验受损 | 置信度降级 + 预览页就地修正（名称/宏量）；Provider 可切换（BYOK） |
| BYOK 门槛高 | 小白流失 | 设置页提供免费 Key 获取引导（Gemini 免费额度） |
| 菜谱生成成本（Token） | 成本不可控 | 每日 5 次限次 + 剩余次数 UI + RECIPE_LOG 缓存复用 |
| 竞品先做大菜谱库 | 差异化减弱 | 强调"拍照×预算×偏好×目标餐次"的个性化闭环而非菜谱数量 |
| 单模块膨胀 | 可维护性下降 | feature 分包；后续拆多模块 |
| 垃圾/过敏内容 | 信任受损 | prompt 排除过敏原；详情页"AI 生成，请自行核对过敏原"免责 |
